# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Quantum Lattice is a PySide6 desktop GUI, styled with `qfluentwidgets` (dark Fluent Design theme), for the `pyqula` tight-binding/DFT-like physics library. The GUI lets a user pick a lattice type/dimensionality, set physical parameters in form fields, and trigger `pyqula` calculations (band structures, DOS, Berry curvature, Chern numbers, self-consistent mean field, etc.), whose results are plotted by standalone plotting scripts. Every lattice mode is a page in one single-process window's sidebar navigation (see "Entry point chain" below) rather than its own separate window/process.

`pysrc/pyqula/` is a vendored copy of the `pyqula` library, developed in a separate upstream repository. **Treat it as a black box: do not hand-edit individual files under `pysrc/pyqula/`.** All work in this repo is on the interface layer that wraps it. Periodically refreshing the whole vendored copy from upstream (`tools/update_pyqula.sh`) is a different thing and is allowed - encouraged, even, from time to time - see "Updating vendored pyqula" below.

See `INTERFACE_GUIDE.md` for a mechanics-level companion to this file: task checklists (adding a term, adding a mode, adding a `ql-*` script) and recorded structural gotchas (e.g. how tabs are actually parented across the shared `QTabWidget`s) that aren't obvious from reading a `.ui` file cold. Its "Per-mode organization map" section is a reference table of how each of the sixteen modern modes differs from the shared conventions (signal wiring, `latticeterms.connect()`/lattice family, SCF, distinctive mechanic) — check it before touching a mode you haven't worked in before, instead of re-deriving its wiring by reading every `<mode>.py`. **Whenever a change touches how the interface is built or wired** — a new dynamic-widget pattern, a new shared convention in `pysrc/interfacetk/`, a newly-discovered structural quirk, a new per-mode checklist item, or a mode's wiring/SCF/lattice-restriction pattern changing — update `INTERFACE_GUIDE.md` (including that map, if it's now stale) in the same change, not as a follow-up.

`docs/user_guide.md` is the end-user-facing counterpart: how to use the app (navigating modes, the shared Geometry/Terms/calculation-tab workflow, SCF, saving results), plus reference tables for every Hamiltonian term and calculation button and a per-mode summary. **Whenever a change is user-visible** — a new mode, a new Hamiltonian term or calculation button, a changed default/behavior, a new mode-specific mechanic — update `docs/user_guide.md` in the same change, not as a follow-up. Unlike `INTERFACE_GUIDE.md`, it should stay free of implementation detail (file names, object names, internal function names) — it's written for someone running the app, not modifying it.

## Running the app

```bash
python install.py                 # checks required packages are importable by this interpreter and
                                   # pip-installs any that are missing (PySide6, PySide6-Fluent-Widgets,
                                   # numpy, scipy, numba, matplotlib; pyvista for the 3D utilities is
                                   # best-effort/optional), registers the `quantum-lattice` console
                                   # script (pip install -e .), and creates a Linux .desktop entry /
                                   # Windows .bat launcher
python install.py --python /path/to/python   # run the install steps with a specific interpreter
                                              # instead of the one running install.py
quantum-lattice                    # launch the app; always runs under whichever interpreter it was
                                    # installed into (pip guarantees this on Linux/Mac/Windows alike)
```

There is no persisted "which Python has the right packages" pin anymore — `pysrc/interpreter/pycommand.py::get_python()` just returns `sys.executable`, since the running interpreter is always the one `pip install -e .` registered the console script into.

Verification is a pytest suite (`python -m pytest tests/`, headless — see `INTERFACE_GUIDE.md`'s "Testing" for its layers and its time/memory budget) plus a manual GUI pass. `tools/smoke_test.py` gives a fast, scriptable first pass across all wired modes (headless, `QT_QPA_PLATFORM=offscreen`): it checks every `QPushButton`/promoted-`PushButton` a mode's page defines (from its `interface.ui`, or from its `formbuilder` spec for a mode that has none) has a wired handler, that the mode script builds its own top-level window and reaches the event loop without crashing when run standalone, and that the shell (`bin/versions/quantum-lattice-pyqt`) builds every mode as a page and reaches the event loop without crashing. Run it after touching `pysrc/interfacetk/`, any `<mode>.py`, or the shell; it catches import/wiring mistakes but does not replace a manual GUI pass for actual physics correctness.

To *see* what a page renders as without launching anything, `python tools/dump_ui.py <mode>` builds it headlessly and writes a diffable widget tree plus one PNG per tab — the reliable way to check a UI refactor changed nothing, since neither `interface.ui` nor the generated `interface.py` reflects the four layers that mutate a page at runtime. See `INTERFACE_GUIDE.md`'s "Seeing what a page actually looks like".

To run a single lattice module directly instead of going through the full shell, each mode still supports a standalone launch that builds just its own top-level window:

```bash
python interface-pyqt/2d/2d.py
```

(this only works because each `<mode>.py`'s blocking `window.run()` call is guarded behind `if __name__ == "__main__"`; when imported by the shell instead, that line never fires and the mode's built page is returned as `window` for the shell to embed).

## Architecture

### Entry point chain

1. The `quantum-lattice` console script (registered by `pip install -e .` via `pyproject.toml`/`quantum_lattice_launcher.py`) or, equivalently, `bin/quantum-lattice` run directly, launches `bin/versions/quantum-lattice-pyqt` as a subprocess under the current interpreter (`sys.executable`), or runs a single utility script if `--utility` is passed to `bin/quantum-lattice`.
2. `bin/versions/quantum-lattice-pyqt` builds a single `qfluentwidgets.FluentWindow` ("the shell") with a left-side `NavigationInterface`. Its `MODES` list drives a loop that, for each mode, adds a lightweight `_LazyPage` placeholder widget to the shell via `addSubInterface()` - not the mode's real page. `load_mode(mode)` (which imports `interface-pyqt/<mode>/<mode>.py` as a page-builder module via `importlib.util.spec_from_file_location`, under a name unique to that mode - `sys.modules["shell_mode_<mode>"]` - and returns its built page, `modobj.window`) only runs the first time the user navigates to that mode: `_LazyPage.ensure_built()` swaps its "Loading..." placeholder child for the real page and caches it, so later visits are free. This keeps launch fast - a mode's business-logic import (and, for some modes, real work done at import time, e.g. `huge_0d` building a default geometry/Hamiltonian) is only paid for modes the user actually opens, not all fourteen up front. The shell's `_on_page_changed()` (wired to `stackedWidget.currentChanged`) is the single place that triggers this build-on-first-visit and re-points `qtwrap`'s active page. Every mode still lives in the **same process and the same `QApplication`**, as a page the user switches to from the sidebar, rather than its own OS subprocess/window. `setTheme(Theme.DARK)` and `os.environ["QL_THEME"]="dark"` are both set once here - the latter is inherited by every `ql-*` plotting subprocess `qlinterface.execute_script()` launches, so `utilities/plotstyle.py` picks a matching dark style with no per-script wiring.

### Per-module structure (`interface-pyqt/<mode>/`)

Every lattice module (`0d`, `1d`, `2d`, `2dslab`, `3d`, `tbg`, `hybridfilm`, `hybridribbon`, `hofstader1d`, `heavyfermion`, `multilayergraphene`, `impurity_embedding`, `ribbon_embedding`, `tmdc`) follows the same three-file pattern (`huge_0d` and `quasiperiodic` are exceptions, see below):

- **`interface.ui`** — Qt Designer form; the only file a human normally edits with a GUI tool. Interactive widgets are promoted to their `qfluentwidgets` equivalents (`QPushButton`→`PushButton`, `QLineEdit`→`LineEdit`, `QComboBox`→`ComboBox`, `QCheckBox`→`CheckBox`, `QRadioButton`→`RadioButton`, `QLabel`→`BodyLabel`) via a `<customwidgets>` block at the end of the file (Designer's "Promote to..." workflow) - each promoted class is still a real subclass of its stock Qt base, so every `isinstance(obj,QtWidgets.QLineEdit)`-style check and every `getattr`/`.text()`/`.currentText()`/`.isChecked()` call in `pysrc/interfacetk/` keeps working unchanged.
- **`interface.py`** — auto-generated from `interface.ui` via `tools/convert_ui.sh` (`pyside6-uic interface.ui -o interface.py`, run for every mode at once). Never hand-edit; regenerate with `tools/convert_ui.sh` after changing any `.ui` file. **Exception: `tmdc` has no `interface.ui`** — its `interface.py` is a hand-written declarative spec consumed by `pysrc/interfacetk/formbuilder.py`, which builds the same widgets and exposes the same `Ui_MainWindow`/`setupUi` interface, so nothing else in the app distinguishes the two paths. That is the pilot for retiring the XML layer mode by mode; see `INTERFACE_GUIDE.md`'s "Declarative pages" for the conversion recipe and the three structural rules a spec must preserve.
- **`<mode>.py`** — the actual business logic: builds the geometry/Hamiltonian from the form values, defines a `signals` dict mapping UI button names to handler functions, and calls `window.connect_clicks(signals)`. This is the file to edit when changing what a module *does*. Its bottom `if __name__ == "__main__": window.run()` only fires on a standalone direct launch (`python <mode>.py`); when the shell imports the module instead (lazily, on first navigation to that mode - see "Entry point chain" above), `window` (the built, wired page) is left for `_LazyPage.ensure_built()` to embed in the shell.

`quasiperiodic/` is a pre-existing, unwired exception — it has no `interface.ui`/generated `interface.py`, imports a stale `interface-pyqt/qtwrap/qtwrap.py` instead of `pysrc/interfacetk/qtwrap.py`, and its `quasiperiodic.py` does not currently run (not wired into the shell's `MODES` list). Left as-is; not part of the modern PySide6/shell architecture described here.

`huge_0d/` is the other exception — its business logic is large enough (KPM-based DOS/spectral calculations, image-to-island geometry construction) that it's split across three files instead of one: `islandbuild.py` (geometry/island construction), `handlers.py` (Hamiltonian building + button handlers), and a thin `huge_0d.py` (bootstrap + signal wiring). `islandbuild.py`/`handlers.py` are plain sibling modules imported with a bare `import islandbuild`/`import handlers` — this works because Python auto-adds a script's own directory to `sys.path` when it's run as `__main__`, the same mechanism `qtwrap.py`'s bare `import interface` already relies on. Their functions take `qtwrap` as an explicit argument rather than reading module-level globals, matching the `common.py` convention.

### Shared toolkit (`pysrc/interfacetk/`)

- `qtwrap.py` — PySide6 glue. One `QApplication` is shared by the whole process (`ensure_app()`), and one module-level `form` pointer tracks whichever page is currently *active* - the one `get`/`getbox`/`modify`/`is_checked`/`set_combobox`/`set_image` (all free functions, reading `form` via `getattr`) resolve against. `new_page(moddir)` builds a mode's page (loads its `interface.py` under a name unique to that mode via `_load_ui_module`, since every mode's generated module defines the same `Ui_MainWindow` class name; dynamically composes a class from `_AppBase` + `QMainWindow` + that `Ui_MainWindow`) and makes it active; `set_active(page)` repoints `form` at a different page (the shell calls this on every navigation change, since only the currently visible page's widgets can receive a click, so one active pointer is always correct even with many pages' widgets alive at once). `_AppBase.connect_clicks()` wraps every handler so it first `os.chdir()`s back into *that page's own* `scratch_dir` (stashed on the page right after `create_folder()`) before running - several pages/modes share one process now, and `pyqula`'s own I/O is cwd-relative, so without this a click on one page could write its results into whichever other page's scratch folder the process cwd was last left in. Each handler then runs on its own worker `_HandlerRunner(QThread)` rather than the GUI thread, so a calculation no longer freezes the shell; widget-touching free functions (`get`/`getbox`/`modify`/`is_checked`/`get_array`/`set_combobox`/`set_image`/`save_interface`/`load_interface`) are decorated with `@_gui_thread_only`, which transparently marshals the call back onto the GUI thread (via a `BlockingQueuedConnection` through `_MainThreadCaller`) when invoked from a handler's worker thread, so handler code in `common.py`/`<mode>.py` needs no changes to run safely off the main thread. Only one handler across the whole shell may run at a time (`is_busy()`/`_busy_lock`) - `pyqula`'s cwd-relative I/O can't tolerate two handlers, or a handler and a newly-built page, `chdir`-ing concurrently, so a second click while one is running is refused with a `qfluentwidgets.InfoBar`, and the shell's `_LazyPage.ensure_built()` defers building a not-yet-visited page until the running one finishes. Progress is shown in the page's own status bar (`IndeterminateProgressBar`) instead of the old separate "Computing..." subprocess window; a failing handler now always raises an `InfoBar.error()` in the window itself (not just a `print()`), so a failure is visible even when launched from the desktop icon with no terminal attached. This intentionally does not support hard-killing a running calculation mid-flight - `pyqula` is vendored/black-box with no cancellation hooks, and safely aborting arbitrary numpy/scipy code would require running it in a separate OS process that gathers its inputs up front instead of reading live widget state throughout, which is a larger follow-up, not part of this change.
- `qlinterface.py` — imports all the `pyqula` submodules used across the GUI, plus process/IO plumbing: `create_folder()` (makes a scratch dir via `tempfile.mkdtemp()` and chdirs into it — calculations run there so `.OUT` files don't clutter the user's directory; portable to Windows, unlike the hardcoded `/tmp` this used to be), `save_outputs()` (copies results back to `<original dir>/QL_save/`), `execute_script()` (parses a command string like `"ql-bands --dim 2"` with `shlex`, then runs it as a `subprocess.Popen([python, scriptpath, *args], ...)` against the `.OUT` files just written, logging stdout/stderr to `<script>.log` in the scratch dir instead of discarding them).
- `qh_interface.py` / `ql_interface.py` — trivial re-export shims (`from .qlinterface import *`, `from .qh_interface import *`); some modules import through these instead of `qlinterface` directly.
- `common.py` — shared business logic reused by most `<mode>.py` files: building operators from a name (`get_operator`), and computing/plotting bands, DOS, KDOS, Berry curvature/phase, Chern numbers, Fermi surfaces, QPI, magnetism, etc. by calling into `pyqula` and then `execute_script`-ing the matching `utilities/ql-*` script. Also `pickup_hamiltonian`/`select_atoms_removal` (the "reload if do_scf is checked, else build fresh" / "write geometry then launch the atom-picker script" logic shared across most modes), and `STANDARD_HANDLERS`/`wire_standard_signals(qtwrap,pickup_hamiltonian,extra={...})` — a registry of button names (`show_bands`, `show_dos`, `show_chern`, ...) whose handler is nothing but `h = pickup_hamiltonian(); common.get_X(h,qtwrap)` in every mode that uses them; a `<mode>.py` only needs to list buttons whose behavior actually differs in `extra`, which always overrides the registry.
- `interfacetk.py` — `modify_geometry` (apply atom-removal/sculpting from the UI's saved selection files, shared across modules that build geometries).
- Hamiltonian-term formulas: every mode calls `common.py:set_formulas(qtwrap)` once, after `connect_clicks()`. For each term name in its `terms`/`meanfield_terms` lists, this sets a rendered-LaTeX image (via `qtwrap.set_logo(t+"_image",t+".png",width=400,height=30)`, pulling `interface-pyqt/logos/<term>.png` — white ink, transparent background) and a physics tooltip (from `TERM_TOOLTIPS`, see below) next to that term's field. A term whose mode has no matching field is silently skipped (`set_logo`/`set_tooltip` no-op on a missing widget name), so one shared `terms` list covers every mode uniformly regardless of which subset of terms it actually has. The `<term>_image` `BodyLabel` itself doesn't have to pre-exist in `interface.ui` — `set_formulas()`'s `_ensure_formula_image()` helper creates it on the fly (one grid column to the right of the field, found via the field's actual containing `QGridLayout`, not `parentWidget().layout()` — Designer nests one grid inside another per term block, see the helper's docstring) the first time a mode without a Designer-authored image widget calls `set_formulas()`. This means **adding formulas to a mode that doesn't have any yet needs no `interface.ui` editing at all** — just make sure the term is in `set_formulas()`'s `terms` list and that mode calls `common.set_formulas(qtwrap)`. `hybridfilm`/`hybridribbon`'s per-part (`_2".."_6"`) term fields use the equivalent mechanism in `hybridparts.py` (`_add_formula_column()`), since those fields are built by `hybridparts.connect()`/`ensure_built()` rather than by `set_formulas()`'s single top-level pass. These PNGs are static bitmaps baked once as white ink, so `qtwrap.set_image()`/`set_logo()` re-tint the pixmap to black/white to match the current theme at load time, and re-tint every already-shown formula label again whenever `setTheme()` fires (`qconfig.themeChanged`). Never `label.setPixmap(QPixmap(path))` a formula PNG directly — go through `qtwrap.set_image`/`set_logo` or it will stay stuck at whatever ink color it was drawn in. **Whenever a new term is added to a mode's interface, add its formula too** — same white-on-transparent PNG convention (matplotlib `mathtext` with `color="white"`, `transparent=True` is enough; no LaTeX/Inkscape install required), added to the `terms` list in `set_formulas()` (or `meanfield_terms` for a new mean-field/many-body term), plus a `TERM_TOOLTIPS` entry (below) — no `interface.ui` edit needed unless the mode in question doesn't call `common.set_formulas(qtwrap)` yet at all, in which case add that call too. `pysrc/pyqula_user_guide.md` and the vendored source's docstrings (e.g. `selfconsistency/spinspin.py::VJinteraction`, `selfconsistency/densitydensity.py::Vinteraction`) are the place to check the exact convention/prefactors for a term before writing its LaTeX, rather than guessing.
- Calculation-button tooltips: every mode also calls `common.py:set_button_tooltips(qtwrap)` once (right after `connect_clicks()`), which sets a hover tooltip on every `PushButton` from the shared `BUTTON_TOOLTIPS` dict (`termtooltips.py`), keyed by object name (`show_bands`, `show_dos`, `solve_scf`, ...) — the same convention as `TERM_TOOLTIPS`, and reused as-is across every mode that has a same-named button, since a "Show bands" button means the same thing everywhere. **Whenever a new calculation button is added to any mode's interface, add its tooltip to `BUTTON_TOOLTIPS` too** — one entry covers that button name in every mode that has it, so check whether an existing entry already fits before adding a near-duplicate.
- `termtooltips.py` — `TERM_TOOLTIPS` (Hamiltonian-term field/formula tooltips) and `BUTTON_TOOLTIPS` (calculation-button tooltips), each a `{name: 1-3 sentence text}` dict shared by `common.py:set_formulas()`/`set_button_tooltips()` and, for `TERM_TOOLTIPS`, also `scfterms.py`/`hybridparts.py` (which build term fields of their own outside `set_formulas()`'s single top-level pass — the mean-field U/V1/V2/J1/J2/J3 tabs and the hybrid modes' per-part fields, respectively). Kept as its own module rather than inline in `common.py` so all of these can import it without depending on each other, and so it can later grow into `{name: {lang: text}}` for multi-language support without touching any caller. **Whenever a new term is added to a mode's interface, add its tooltip to `TERM_TOOLTIPS`; whenever a new calculation button is added, add its tooltip to `BUTTON_TOOLTIPS`** — one 1-3 sentence entry, focused on physical meaning for a term (what it represents, what symmetry it breaks/preserves, what effect it produces) or on what gets computed/plotted for a button.
- `latticeterms.py` — registry of Hamiltonian terms/operators only valid for certain lattice families (currently: Haldane, Kane-Mele, and the "valley" operator, all honeycomb-only). A mode wires it up with one call, `latticeterms.connect(qtwrap,lambda: getbox("lattice"))` (or a constant lambda for a mode whose geometry is always honeycomb-derived regardless of UI choice, e.g. `tbg`/`multilayergraphene`), placed once after its `LATTICES`/`lattices` dict is defined - see `2d.py`, `0d.py`, etc. `connect()` shows/hides the registered widgets and toggles the registered combobox items every time that mode's own "lattice" combobox changes (and once immediately). Adding a new geometry-restricted term later is a one-line addition to `RESTRICTED_TERMS`, no other code needs to change.
- `labels.py`, `saveload.py`, `debugging.py`, `plotpyqt.py` — minor helpers (form label text, save/load interface state to JSON, an error-visibility toggle, matplotlib-in-Qt helpers).

### `utilities/` (`ql-*` scripts)

Standalone executable Python scripts, one per plot/postprocessing task (`ql-bands`, `ql-dos`, `ql-structure-bond`, `ql-berry2d`, `ql-chern-evolution`, ...). They are never imported — they're launched as separate processes by `execute_script()` against the `.OUT`/data files a `<mode>.py` handler just wrote in the scratch folder. When adding a new kind of result to visualize, the usual pattern is: write a `.OUT` file from the handler in `<mode>.py`/`common.py`, then add/extend a `ql-*` script to read and plot it.

The 3D scripts (`ql-moments`, `ql-magnetism`, `ql-structure3d`, `ql-plot3d`, `ql-pick`, ...) use **PyVista** (real VTK rendering: lighting, true spheres/tubes, interactive point picking) via the shared `utilities/_pv3d.py` helper (`new_plotter`, `add_atoms`, `add_bonds`, `add_arrows`, `add_trisurf`, `enable_point_picking`). PyVista replaced mayavi here: mayavi's own `tvtk` wrapper-generation step fails to build on newer Python, whereas PyVista installs from prebuilt wheels. `_pv3d.py` is not a `ql-*` command — it's only imported by sibling scripts via `sys.path.insert(0, dirname)`, same pattern every `ql-*` script uses to find its own directory. PyVista is an optional/best-effort dependency (see `pycommand.py`), so these scripts should fail informatively (import error) rather than silently if it's missing, not crash the whole app.

### Updating vendored pyqula

`tools/update_pyqula.sh` refreshes `pysrc/pyqula/` (and its paired `pysrc/pyqula_user_guide.md`) from `https://github.com/joselado/pyqula` master, wholesale - it deletes and replaces the whole directory rather than patching it in place, matching how it was vendored in the first place. This is allowed, and worth doing from time to time (e.g. before relying on a `pyqula` feature that might have landed upstream recently, or just periodically to stay current) - it's a different thing from hand-editing files under `pysrc/pyqula/`, which is still off limits. After running it: re-run `tools/smoke_test.py`, skim `git diff --stat pysrc/pyqula` for anything alarming (removed/renamed functions this repo's interface layer calls), **check upstream's `pyproject.toml` (`[project].dependencies` - not `optional-dependencies`, which are lazily-imported-only extras) against `requirements.txt` and add/update any entries that drifted**, and commit the refresh as its own commit, separate from unrelated work - see `git log --oneline -- pysrc/pyqula/` for the commit-message convention prior updates used.

`pysrc/pyqula_user_guide.md` is upstream's own tutorial/feature guide (`documentation/user_guide.md` in the `pyqula` repo), refreshed by the same script. Since `pysrc/pyqula/` is a black box you're not meant to read for its own sake, check this file first when you need to know whether some physics/calculation is already implemented in `pyqula` and how to call it, instead of grepping through the vendored source.

### `pysrc/interpreter/`

`pycommand.py` is the install/launch toolbox: `get_python()` returns `sys.executable`, `install_requirements()` checks each required package by trying to import it under the target interpreter and pip-installs only what's missing (pyvista is attempted best-effort and never fails the install), `install_editable()` runs `pip install -e .` to register the `quantum-lattice` console script, `create_icon()`/`get_qh_command()` build a Linux `.desktop` entry or Windows `.bat` launcher, preferring the pip-installed script (found via `shutil.which`) since desktop launchers often run with a minimal `PATH`.

### Packaging

`pyproject.toml` + `quantum_lattice_launcher.py` (a single top-level module, not part of `pysrc/`) register the `quantum-lattice` console script via `pip install -e .`, without restructuring how the rest of the codebase is imported — everything under `pysrc/`/`interface-pyqt/` is still reached at runtime through the existing `sys.path.append(qlroot+"/pysrc/")` bootstrap, unchanged. `requirements.txt` is the source of truth for required packages; `pycommand.py::_required_packages()` reads it directly.

### Data flow summary

shell registers a lightweight placeholder for every mode at startup, building only the initially-shown one → user navigates to a mode's page (building it on that first visit if it hasn't been opened yet this session) and sets parameters in its `interface.ui` fields → clicking a button restores that page's own `tempfile.mkdtemp()` scratch dir as the process cwd (`qtwrap._AppBase.connect_clicks()`, see above) → handler builds a `pyqula` geometry/Hamiltonian using `get`/`getbox` values → computation runs in that scratch dir → results written as `.OUT` files → matching `utilities/ql-*` script launched (logged, non-blocking, inheriting `QL_THEME=dark` so `plotstyle.apply()` matches the shell's theme) to plot them → (optionally) `save_outputs()` copies the scratch dir back to `QL_save/` in the directory the shell itself was launched from.
